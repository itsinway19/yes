# BuilderAd engineering standards

This is an implementation guide, not product governance or an execution backlog. The sole design authority is the [governing Markdown](../architecture/BUILDERAD_GOVERNING_ARCHITECTURE.md); [current implementation](../architecture/CURRENT_IMPLEMENTATION.md) distinguishes shipped, local and unproven behavior. The rules below preserve existing executable contracts. Future requirements are labelled explicitly.

## Authority and data rights

| Boundary | Required behavior | Existing owner / protection |

Team membership, agency assignment, Source connection and a visible control grant no other access. | [BusinessScope](../../app/Foundation/Business/BusinessScope.php), [PrincipalContext](../../app/Foundation/Tenancy/PrincipalContext.php), [BusinessScopeFoundationTest](../../tests/Feature/BusinessScopeFoundationTest.php), [BusinessDelegationTest](../../tests/Feature/BusinessDelegationTest.php), [BusinessAgencyOwnershipTest](../../tests/Feature/BusinessAgencyOwnershipTest.php). |

Document evidence is request evidence, not a reusable grant. | [SessionAuthority](../../app/Security/SessionAuthority.php), [CommercialContext](../../app/Commercial/CommercialContext.php), [SessionAuthorityTest](../../tests/Feature/Security/SessionAuthorityTest.php). |
| PostgreSQL/RLS | Runtime `pgsql` uses `builderad_app`; schema ownership uses `pgsql_migrations` / `builderad_owner`; trusted issuance uses separately restricted `pgsql_authority`. Preserve RLS, private-function privileges, signed context, permits and transaction-local lifetime. Never use owner credentials to make application behavior pass. | [database configuration](../../config/database.php), [bootstrap](../../database/bootstrap/postgresql.sql), [DatabaseAuthorityBoundaryTest](../../tests/Feature/Security/DatabaseAuthorityBoundaryTest.php), [BusinessFinalBoundaryTest](../../tests/Feature/BusinessFinalBoundaryTest.php). |

Do not change authority semantics, isolation, lock order or critical timeouts merely to pass a test. A genuine authorized contract change requires its applicable owning decision and boundary tests. SQL/migration engineering within an authorized task is normal work; protections depend on impact, not filename.

## Facts, versions and compatibility

- Keep one owner for each fact and operation. Declared markets are not location, fulfillment coverage or provider targeting; goal preferences are not achieved outcomes; inquiry assertions are not independently verified buyers, payments or profit. Owners: [BusinessScope](../../app/Foundation/Business/BusinessScope.php), [AdvertiserGoalPreferences](../../app/Business/AdvertiserGoalPreferences.php), [InquiryEvidence](../../app/Commercial/InquiryEvidence.php). Tests: [BusinessPreferenceVariantsTest](../../tests/Feature/BusinessPreferenceVariantsTest.php), [InquiryEvidenceAdmissionTest](../../tests/Feature/InquiryEvidenceAdmissionTest.php).
- Keep source/provider transport outside declared Core boundaries. The recursive [CoreDependencyBoundaryTest](../../tests/Unit/CoreDependencyBoundaryTest.php) protects `app/Business`, `Foundation`, `Sources`, `Commercial`, `MarketKnowledge`, with its two explicit existing exceptions. [ArchitectureSourceOptionalityTest](../../tests/Feature/ArchitectureSourceOptionalityTest.php) protects bounded zero-provider operation; neither test proves arbitrary indirect dependencies or all future sources.
- Preserve question, method revision, result meaning and evidence references. A caller cannot register a class/method/schema by naming it. Change both installation/upgrade definitions and consumers when a real contract requires it; unknown or unsupported semantics must fail closed.
- HTTP/OpenAPI contracts live in [application.openapi.json](../../contracts/application.openapi.json) and [goals.openapi.json](../../contracts/goals.openapi.json); generated clients/types have their own checked-in owners. Use `npm run api:check` for drift and `npm run api:generate` only for authorized contract changes. No PHP-only half-fix when SQL/API/TypeScript also owns the affected boundary.

## Independent validation and trusted completion

The existing analytical boundary is `MarketMethodSelector → MarketMethod → Findings → MarketProcessing → TrustedCompletion → SQL`. [Findings](../../app/MarketKnowledge/Processing/Findings.php) validates the envelope and exact question/revision. [OfferEquivalenceResult](../../app/MarketKnowledge/Processing/OfferEquivalenceResult.php), [QualifiedInterestChangeResult](../../app/MarketKnowledge/Processing/QualifiedInterestChangeResult.php) and [BusinessFeasibilityResult](../../app/MarketKnowledge/Processing/BusinessFeasibilityResult.php) independently validate the three admitted v1 meanings and classify validated and abstained results. The validators merged in PR #68 with [post-merge Foundation evidence](https://github.com/42Huss/builderad/actions/runs/43714626327).

Preserve independent recomputation, comparability and exact disclosure fields; schema shape alone cannot certify a judgment. Do not delegate sole acceptance to the selected executor. Failure, unavailability, cancellation and abstention are distinct from an approved finding. New revisions require their own admitted meanings and independent validator; no default success for an unknown state.

[MarketProcessing](../../app/MarketKnowledge/Processing/MarketProcessing.php) releases database transactions before computation. [TrustedCompletion](../../app/MarketKnowledge/Processing/TrustedCompletion.php) and [KnowledgePublisher](../../app/MarketKnowledge/KnowledgePublisher.php) preserve separate attestation, current authority and atomic consumption. SQL binds completion to the result/run/command/actor/generation/session/Business/method/backend/transaction. Protection: [MarketProcessingCompletionSecurityTest](../../tests/Feature/MarketProcessingCompletionSecurityTest.php), [MarketKnowledgeCompletionSecurityTest](../../tests/Feature/MarketKnowledgeCompletionSecurityTest.php), and the existing concurrency suites. Do not bypass these owners to introduce another publication path.

## History and migrations

Corrections, withdrawal and changed current eligibility must not silently rewrite prior meaning or grant continued use of ineligible data. Preserve source versions and scoped lineage; invalidate/review actual dependent results, not unrelated knowledge. Protection: [MarketKnowledgePublicationTest](../../tests/Feature/MarketKnowledgePublicationTest.php), [MarketBusinessFindingTest](../../tests/Feature/MarketBusinessFindingTest.php), [CustomerDiscoveryPracticeTest](../../tests/Feature/CustomerDiscoveryPracticeTest.php), [BusinessHistoryTest](../../tests/Feature/BusinessHistoryTest.php).

Accepted migration/input bytes are checked against an independently pinned Git baseline by [MigrationInputIntegrity](../../tests/Support/MigrationInputIntegrity.php), [its tests](../../tests/Unit/MigrationInputIntegrityTest.php) and [migration-inputs.lock.json](../../tests/Fixtures/migration-inputs.lock.json). Do not edit protected historical migrations or authorize them by updating candidate hashes. The special Workspace-retirement transition is fixed in the existing guard; it is not a general rebaseline facility.

New SQL migrations use the guard's supported literal `DB::statement`/`DB::unprepared` convention or literal `file_get_contents(database_path('migration-sql/<migration-stem>/<file>.sql'))` inputs; register actual readers/hashes under the existing manifest contract. Check the guard's accepted syntax before extending it. A required new mechanism needs its own reviewed protection, not a bypass. Test fresh installation, populated upgrades, repeatability and permissions when the actual change affects them. Fresh-install proof does not certify production upgrade execution.

## Commands, retries and external effects

Use each operation's existing command identity, expected revision, receipt and current authority. Preserve exact retries; conflicting payloads must not reuse an old command. Unknown network outcome is not failure, permission to invent a replacement command or permission for blind replay. A receipt does not itself prove commercial success. Existing owners: [BusinessScope](../../app/Foundation/Business/BusinessScope.php), [RegisterCommercialScope](../../app/Commercial/RegisterCommercialScope.php), [CommercialContext](../../app/Commercial/CommercialContext.php), and provider-specific execution boundaries such as [MetaReadExecution](../../app/Providers/Ads/Meta/MetaReadExecution.php).

For concurrency proof, observe worker readiness, the actual contending connection and blockers, early exit and final outcome. A timeout alone does not establish a product defect; one isolated retry is not proof of flakiness. Use existing [MarketProcessingConcurrencyTest](../../tests/Feature/MarketProcessingConcurrencyTest.php) and [MarketKnowledgeConcurrencyTest](../../tests/Feature/MarketKnowledgeConcurrencyTest.php) as bounded examples, not as a universal concurrency framework.

Future AI, remote writes, learning, subscription and automation must use qualified inputs, explicit scope/cost/failure contracts, the appropriate independent validation and separate execution approval. These are design conditions from the governing architecture, not claims that those systems exist. Do not infer lawful cross-Business training, quota reservation, reconciliation of unknown remote effects or causal learning from current local method tests.

## User experience and lifecycle

The implementation appearance context is [DESIGN.md](../../DESIGN.md). Preserve actual runtime owners rather than historical screen sequences:

- [transport.ts](../../resources/js/spa/transport.ts), [router.ts](../../resources/js/spa/router.ts), [presentation.ts](../../resources/js/spa/presentation.ts) and [browserLifecycle.ts](../../resources/js/spa/browserLifecycle.ts) own document identity, admission, navigation candidates, synchronous concealment and restoration. Read plus current witness precedes publication; stale responses cannot publish into another identity/resource/candidate. A terminal document does not reopen or adopt another Principal.
- Unsent drafts retain their originating versions in the applicable document/Business/authority scope. Drafts and local navigation grant no data access. Password/authenticator material is not ordinary draft storage. Pending/unknown commands keep their identities and are never automatically resent on return.
- Returning to a retained private panel requires fresh display qualification. Denial, closure or identity/context changes conceal protected data synchronously. Read authority remains independent of write authority. Tests: [SPA presentation](../../tests/spa-presentation.test.mjs), [browser lifecycle](../../tests/spa-browser-lifecycle.test.mjs), [inquiry evidence](../../tests/inquiry-evidence.test.mjs), [Business activity](../../tests/business-activity.test.mjs).
- Inquiry acceptance definitions stay bounded plain text in their immutable source-asserted revisions, distinct from criterion version. Missing historical meaning remains unknown; render through escaped interpolation. Contact/code/reference rejection is a bounded safeguard, not universal PII detection or independent verification. [InquiryEvidenceAdmissionTest](../../tests/Feature/InquiryEvidenceAdmissionTest.php) protects these contracts; no external criteria registry is implied.
- Preserve Arabic RTL/English LTR behavior, focus, keyboard navigation, accessible errors and recovery. A user-facing capability needs its actual visible job, placement/context/authority and denied/missing/unknown states, plus appropriate browser evidence. `BACKEND_VERIFIED`, `UI_INTEGRATED` and `BROWSER_VERIFIED` remain distinct evidence labels, not automatic promotion states. No new screen is required for an internal primitive.

## Verification and evidence

Use [README](../../README.md) for prerequisites. The complete hosted gate is [foundation.yml](../../.github/workflows/foundation.yml); the official Windows isolated runner is [Test-GoalsSpa.ps1](../../scripts/Test-GoalsSpa.ps1). Never run destructive tests against preview/shared data. Direct wrapper tests require a prequalified disposable database and all three restricted/owner/issuer identities; the isolated runner manages these explicitly.

| Change | Smallest appropriate starting point |
|---|---|
| Documentation | Check content, links, source/reading-copy parity and `git diff --check`; inspect any direct README/script consumers. No automatic Foundation. |
| Local Vue behavior | Relevant existing `test:*` or Node test files; rendered/browser verification for changed interaction, RTL, viewports and accessibility. |
| Router/transport/presentation | `pwsh -NoProfile -File scripts/builderad.ps1 npm run test:visibility`; expand to affected browser lifecycle checks. |
| PHP/domain/API | `pwsh -NoProfile -File scripts/Test-GoalsSpa.ps1 -Phase Focused -TestFilter 'BusinessFoundationTest'` with actual affected class selection; API changes also `scripts/builderad.ps1 npm run api:check`. |
| SQL/authority/schema | Same Focused runner with the actual boundary/migration/concurrency classes, including success and denial, currentness and upgrade/fresh behavior as affected. |
| Complete JavaScript / production build | `scripts/builderad.ps1 npm test`; `scripts/builderad.ps1 build`. One production build per comprehensive gate; `build:goals-spa` is an alias, proof mode is separate. |
| Browser lifecycle / Business journeys | Production build, then `scripts/Test-GoalsSpa.ps1 -Phase Browser -BrowserSelection foundation` or `businesses` as applicable. Inspect supported selections and fixture requirements in the runner; instrumented proof selections remain separate. No screenshots without approval. |
| Applicable comprehensive gate | Prefer authorized hosted Foundation on the actual candidate. Local equivalent: `pwsh -NoProfile -File scripts/Test-GoalsSpa.ps1 -Phase Foundation`. Do not publish just to obtain it without authorization. Browser evidence is separate. |

Choose tests by impact, not extension or count of changed files. Before diagnosing a failure, establish the last relevant authoritative PASS, candidate changes and materially comparable runner/database/fixture conditions. Start with discriminating probes; do not change production semantics merely to match a test expectation. Stop unproductive expansion after two probes and identify the smallest useful next step.

Passing evidence applies only to matching executable source, dependencies, configuration and conditions. Dirty-tree proof needs a manifest/hash or exact tested change description. Preserve failures and limits; absent/blocked/unexecuted gates are not PASS. Reuse unaffected passing checks; after a correction rerun affected checks rather than automatically repeating a comprehensive suite. Final acceptance and deployment are separate from focused development verification. Track and clean only task-owned processes/resources.
