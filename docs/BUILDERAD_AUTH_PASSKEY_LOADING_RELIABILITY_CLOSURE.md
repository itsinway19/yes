## 4. Gate A — رفض نشر المظهر

السبب المثبت: `appearance/state.ts` كان يعامل 403 كله كفقد سلطة ويستدعي `close()`؛ إغلاق العرض يستدعي clear ويمسح المسودة ويخفي السبب. الاختبارات القديمة استبدلت close بدالة فارغة، ولذلك لم تثبت تجربة الرفض كاملة.

التصحيح:

1. يمر رفض الحداثة عبر استجابة صريحة `code=fresh_authentication_required` و`reauthenticate`، بدل الاكتفاء بنص/403. يعود عبر middleware قبول المستند، فيحمل ربط الهوية الحالي.
2. يثبت متحكم المظهر Founder و`grant.manage` قبل عرض رفض الحداثة القابل للتعافي. يعاد التحقق من Founder/grant داخل معاملة النشر كما كان. بذلك لا يحجب انتهاء الحداثة فقد الصلاحية الحقيقي.
3. لا يقبل Transport هذا التصنيف إلا مع metadata مطابقة وربط principal مصادق عليه ومسار التعافي المعتمد داخل boundary. metadata مفقودة/مختلفة/JSON تالفة/null/array تُغلق المستند.
4. Vue تحتفظ بالمسودة ضمن المستند المصرح الحالي، وتعرض سببًا عربيًا/إنجليزيًا محددًا ورابط `/internal/identity/switch` الحقيقي، وتحجب تكرار POST. المسودة لا تُنقل تلقائيًا عبر انتقال Principal أو إلى مستند جديد؛ توضح الواجهة أنها تبقى إلى أن يغادر المستخدم الصفحة.
5. تعارض revision يبقى stale؛ Lost ACK يبقى unknown؛ لا إعادة نشر تلقائية ولا استنتاج نجاح من 409.

التحقق الحقيقي شمل: رفض حداثة 403 مع بقاء المسودة؛ فتح مسار إعادة المصادقة ووجود زر Passkey الفعلي دون الضغط عليه؛ receipt غير صالح 409؛ فقد grant؛ إلغاء session؛ اختفاء المسودة المحمية بعد close؛ revision conflict؛ Lost ACK وعدم التكرار؛ النشر المأذون وأثره على المستندات الجديدة للمعلن؛ RTL/عرض جوال/تركيز وتباين.

اختبار receipt يستخدم دليلًا غير صالح عبر الطلب الفعلي؛ لا يُوصف كإثبات BFCache أو إعادة عرض وثيقة من compositor.

## 5. Gate P — المفتاح والإقرار

المهلة القائمة 10000ms تخص طلب fetch وقراءة رده في Transport؛ لا تحيط بانتظار `startAuthentication`/مراسم المستخدم. لم تُمدد.

الفجوة المثبتة في التشخيص: `runPasskeyOperation` أنشأ معرف correlation في URLs ثم تجاهلت شاشة الدخول هذه URLs؛ لم تكن معرفات المحاولة تصل إلى Laravel. أصبح المعرف العشوائي غير السري يصل في `webauthn_probe` إلى طلب الخيارات وطلب assertion، مع عقد OpenAPI قابل للتوليد.

تسلسل القياس الحالي:

`challenge request → challenge reply → credential request/start/end → assertion request → server verification/start/end → server accepted → transport acknowledgement admitted → new authenticated document usable`.

يسجل الخادم محليًا مراحل ومدة monotonic منذ أول trace داخل الطلب؛ هذه ليست مدة Laravel الكاملة أو زمن الشبكة. يسجل Transport مرحلة قبول الإقرار قبل close/native navigation، لأن promise المكوّن قد تزول مع المستند القديم قبل استئنافها. سجلات العميل JSON نصية كي تبقى قابلة للرصد عبر الانتقال. لا cookies أو tokens أو challenges أو assertions أو credential IDs أو بيانات شخصية في القياس المضاف.

الأزمنة داخل العميل والخادم مستقلة؛ لا طرح بين ساعتي جهازين. زمن HTTP وزمن واجهة قابلة للعمل لا يُساويان زمن WebAuthn البشري.

حالات النتائج:

| الحالة | السلوك المقبول |
|---|---|
| إلغاء قبل إرسال assertion | رسالة إلغاء؛ لا POST للدخول |
| رفض WebAuthn صريح/توقيع غير صالح/تحدّ منتهٍ | رفض معلوم من الخادم؛ لا نجاح ولا replay |
| التزام الدخول بالخادم وفقد ACK | UNKNOWN؛ زر إعادة الإرسال محجوب؛ فتح مستند جديد يقرأ الجلسة الحالية دون إعادة assertion |
| ACK مطابق | يتحقق Transport من lineage/epoch/nonce/boundary ثم يغلق القديم وينتقل لمستند جديد |
| ACK أو metadata من هوية/جيل مختلف | لا قبول ولا استعادة للبيانات القديمة |

ظهر فشل قياس في المحاولة المكتبية الأولى بعد نجاح الدخول: مرحلة مسجلة بعد await API لم تُرصد عبر زوال المستند؛ صُحح موضع القياس ولم تُغير المصادقة للحصول على PASS.

الهاتف المتأثر: أبلغ المالك أنه **Android، وأن الخطأ يظهر بعد البصمة**. الطراز وإصدار النظام والمتصفح غير محددة، ولم تُرصد محاولة مترابطة من الجهاز: **NOT OBSERVED**. لا يُنسب العطل النهائي لمهلة 10 ثوانٍ، ولا يُدّعى إصلاح الهاتف من virtual authenticator.

في البناء النهائي سُجل قبول الإقرار أولًا، ثم `document_disposed` و`disposed` عند مغادرة المكوّن. هذا تنظيف المستند بعد الانتقال؛ لا يُصنف كإلغاء المستخدم أو فشل مصادقة. بقي استدعاء الإلغاء الحقيقي وحارس العملية حتى الاستقرار كما كانا.

## 7. Gate E — البيئة

الأربعة مستويات فُحصت منفصلة:

| المستوى | الخلل الأولي | التحقق بعد الإجراء |
|---|---|---|
| composer.json/lock | لا تبعية Inertia مقبولة | القفل لم يتغير |
| installed/vendor | `inertiajs/inertia-laravel v3.3.4` زائدة من نسخ vendor السابق | `composer install --no-interaction --prefer-dist --no-progress` أزال حزمة واحدة، دون تثبيت/تحديث حزم؛ inventory مطابق في الاتجاهين |

| runtime | تحميل provider قديم ممكن من الكاش الملوث | bootstrap فعلي: provider غير محمل، class لا تحل، ملفات الحزمة غائبة، config غير cached |

تحذير Composer عند pre_uninstall للحزمة القديمة محفوظ بوصفه أثرًا للبيئة الملوثة؛ لم يُخفَ، وأكمل Composer الإزالة والاكتشاف بنجاح. لا يُنسب سلوك Vue السابق إلى تلك الحزمة دون دليل.

## 8. التحقق والمراجعة

- اختبارات عميل مركزة نجحت، ومنها fresh-auth metadata المفقودة/المختلفة/التالفة، الحفاظ على draft وحجب إعادة النشر، وقيود ACK/الحدود والإلغاء والـrenewal.
- Laravel المركز: **84 PASS / 868 assertions** عبر المشغّل الرسمي المعزول؛ GlobalAppearance، IdentityDocument، ProductionIdentity، SessionAuthority، IdentityRenewal، ProductionPasskey، PasskeyBoundary، CoreDependencyBoundary، ArchitectureSourceOptionality.
- تشغيل المظهر السابق: **12 حالة سلوكية ناجحة و43 مطابقة asset hash** مع الملفات المحلية؛ نتيجة محتفظ بها لذلك المصدر والبناء. أصول production، مستخدمون اصطناعيون، CSRF حقيقي، SQL وRedis حقيقيان. ليست إثباتًا لتشغيل نهائي كامل بعد إضافات harness.
- مراجعة مستقلة قرائية عبر subagent: وجدت مسار malformed JSON؛ صُحح واختُبر. إعادة المراجعة لم تجد blocker في fresh-auth أو trace أو Composer. هذه مراجعة source وليست بديلًا لاختبارات التنفيذ أو قبول الهاتف.
- اختبارات العميل الكاملة: **330 PASS، صفر فشل/تخطي** بالاختيار الرسمي، serial كما في مشغّل Windows. نجحت `inertia:check`، `composer validate --strict`، `composer audit`، `npm audit --audit-level=high`، `api:check`، Pint، بناء production، و`runtime-retirement --assets`. تدقيقا الاعتمادات لم يجدا ثغرات. النتائج في `recovery-gate-results.json` وسجلات `recovery-gate-*`.

### Foundation وإعادة الاختبار المحدودة

تشغيل PHP الشامل الرسمي أكمل الاختيار: **1024 PASS، حالتان فاشلتان، 15518 assertions، 1965.30s**. المصدر ظل ثابتًا (`source-unchanged=True`). نتيجة التشغيل **FAIL**، والسجلات الأصلية محفوظة باسم `ebaf81b1-4a35-4f0a-b7ea-ead6df33c27b-tests.*` مع `events.log`.

1. `CurrentIntentConcurrencyTest::test_preacquisition_expiry_revocation_and_prepared_entry_invalidation`: فشل كتابة دليل بـ`errno=28 No space left on device`. هذا سبب تخزين بيئي مثبت، وليس assertion يثبت خلل منتج.
2. `CommercialMarketPreparationTest::test_two_independent_sessions_cannot_consume_the_same_target_twice`: تجاوز عامل مهلة 20s، بمخرجات فارغة. أثر العامل وصل إلى نهاية autoload (~3970ms) ولم يسجل اكتمال bootstrap أو جاهزية أو محاولة قفل. سبب التوقف السابق للجاهزية غير محسوم؛ لا يكفي timeout لإثبات خلل تنازع SQL، ولا نجاح الإعادة لتسميته flaky.

بعد تحرير المساحة، نجحت إعادة الحالتين عبر المشغّل الرسمي المعزول: **2 PASS، 114 assertions، 24.72s**. لم تتغير نافذة زمنية أو assertion أو SQL. اختبار التزامن يفرض رصد waiter حقيقي في `pg_locks` وحامل حي قبل release؛ اجتازها، ثم انتهى العاملان بـ200 و409 وكتابة واحدة. إيصال `commercial-worker-010e080f-2be3-4cdd-a771-5557718cf057.json` يسجل bootstrap والجاهزية والمخرجات؛ أدلة `intent-race-*` السبعة اكتملت دون خطأ تخزين. توفر نحو1.21GiB وحده لم يُعامل كإثبات؛ اكتمال الإعادة وكتابة الأدلة هو الدليل. محاولة ترشيح سابقة بصيغة `Class::method` لم تُقبل: **صفر اختبارات**؛ حُفظت ولم تُحسب نجاحًا، ثم استُخدمت أسماء الحالتين المقبولة.
