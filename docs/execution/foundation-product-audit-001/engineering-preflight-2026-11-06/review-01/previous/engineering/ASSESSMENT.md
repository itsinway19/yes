# BuilderAd — دراسة المخاطر والاختيارات الهندسية قبل التنفيذ

التاريخ: 6 نوفمبر 2026. النطاق: الحزمة المقترحة لسياق النشاط والعرض والسوق، وتكاملها مع الأقسام والأدلة والقرار وAI والأتمتة. الحالة: **`PATH_RECOMMENDED_WITH_PACKAGE_GATES / PERFORMANCE_UNMEASURED`**.

هذه دراسة قبل التنفيذ ضمن سجل التدقيق الحالي. ليست إعادة تصميم للمنصة، ولا تدقيقًا أمنيًا شاملًا، ولا اختبار تحميل، ولا إعلان جاهزية إنتاجية. لم يعدل كود التطبيق أو SQL أو الاعتمادات، ولم تجر اتصالات بقواعد المعاينة/المالك أو بحسابات إعلانية. لا Foundation جديد ولا نشر أو دمج.

## 1. القرار الهندسي

نبدأ من التطبيق الحالي وأصحاب مسؤولياته. نضيف عقدًا محدودًا يحتاجه مستهلك تجاري فعلي، ثم نثبت رحلة متصلة؛ لا نبني «محرك قطاعات» أو «محرك ذكاء» أو نظام صلاحيات موازٍ. تتعاون الأقسام عبر حقائق ومراجع وإصدارات ونتائج مؤهلة، ولا يكتب كل قسم نسخته من سياق النشاط أو النتيجة.

المكدس الموجود حديث ومدعوم في الإصدارات الرئيسية المفحوصة. لا دليل من هذه الدراسة يبرر استبدال Laravel/Vue/PostgreSQL أو توزيعها إلى خدمات مستقلة. الترقيات التصحيحية المنتظمة مهمة، أما الترقية الرئيسية أو إضافة تقنية فتحتاج فائدة محددة ومقارنة وتحققًا من التوافق. وثائق المورد تثبت الخاصية المنشورة، لا ملاءمة BuilderAd أو أداءه أو أمانه تلقائيًا.

أعلى التبعيات المثبتة سابقًا: G-01 لاستعمال ملاحظات المصدر المباشر، G-02 لواجهة مستهلك المعرفة، G-03/05 لحقائق العرض والنتيجة، G-04 لتنفيذ إعلان، وG-07 لحصص/اشتراك خدمة مشروطة. هذه نواقص محددة؛ لا تثبت انهيار الأساس كله. بقية مخاطر السجل احتمالات يجب منعها أو قياسها عند إدخال التغيير، وليست عيوبًا جديدة مثبتة.

**قواعد الاتصال:** يحمل العقد الحد الأدنى اللازم من business/offer/scope/revision/evidence references وفق معناه؛ لا metadata موحدة ضخمة مفروضة على كل دالة. الكاتب المعتمد وحده يغيّر الحقيقة؛ القارئ لا يكتب إلى جدول مجال آخر مباشرة. API للعرض/القراءة أو أمر الخادم هو الحد، لا استدعاء Vue لمكوّن كي يصبح صاحب حقيقة. يذكر كل مشتق مدخلاته المؤثرة ونسخها وسبب صلاحيته، بما يكفي لتأهيله بعد التصحيح.

تغيير سوق مستهدف لا يعيد تسمية سوق بيع تاريخي ولا يمنح حق مصدر. تصحيح عرض يعيد تقييم المشتقات المعتمدة عليه فقط؛ لا يعيد تشغيل كل الأقسام. ما نعرضه تاريخًا ليس دليلًا حاليًا تلقائيًا. الاستعلام الجديد/التنفيذ يعيدان تأهيل السلطة؛ التخزين المؤقت ليس بديلًا لذلك. يظل البحث/التخطيط/القياس والفعل في علاقات متبادلة، دون pipeline إجباري «قطاع→سوق→إعلان» لكل وظيفة.

## 5. المخاطر ذات الأثر الأعلى والمسار المضاد لها

السجل الكامل `RISK_REGISTER.csv` يضم24 بندًا؛ التصنيفات: `CONFIRMED_GAP` فجوة موثقة في النسخة، `DESIGN_RISK` خطأ محتمل عند الامتداد، `MEASUREMENT_REQUIRED` أثر أو كفاية غير مقاسين. `BEFORE_DEPENDENT_CAPABILITY` يعني قبل القدرة المتأثرة فقط، وليس منع كل تنفيذ مستقل. لم تُحسب احتمالات أو درجات أمان مصطنعة.

1. **إعادة بناء السياق أو تغيير معناه:** نبدأ بمطابقة BusinessScope وSQL والحقول ومستهلكيها. نفصل التخصص والعرض والسوق الحالي والمستهدف والخدمة عند الحاجة؛ لا ننقل declared_markets القديمة إلى معنى جديد صامتًا. التصنيف مدخل، وليس خوارزمية. يثبت اختبار اختلاف دلالي وثبات عند اختلاف شكلي.
2. **فتح حق جديد ضمن حقل يبدو بسيطًا:** العرض أو الهامش أو التاريخ قد تكون بيانات خاصة. لا نفترض أن context.read أو عضوية Workspace يجيزان كل معلومة جديدة. نثبت الكاتب والقارئ والعمليات والتاريخ والرفض داخل SQL/العقد القائم؛ لا permission engine في Vue أو LLM.
3. **سياق قديم بعد تبديل النشاط:** النقل الحالي يستعمل revision/AbortController والتحقق من الهوية، وQueryClient يمسح عند إغلاق المستند؛ هذه حماية قائمة لا عيب مثبت. المستهلك الجديد يضيف النطاق الذي يعتمد عليه إلى مفاتيحه، ويعيد تأهيل الرد قبل عرضه. لا يُكتفى بالإلغاء؛ الخادم قد يكون نفذ أمرًا بالفعل.
4. **الرفض والتعارض والنتيجة المجهولة:** 422 المثبت قبل التنفيذ يتيح تصحيح المدخلات وأمرًا جديدًا؛409 يتطلب تحديث الحالة ومراجعتها؛ انقطاع الرد يبقي الأمر الأصلي للمصالحة. لا retries تلقائية لأثر مالي أو كتابة غير معروفة، ولا إعادة توجيه عامة تخفي الأمر. يعاد استخدام مالك التعافي الحالي.
5. **SQL الصحيح جزئيًا والمخطط النهائي الخاطئ:** نراجع إعادة تحميل التعريفات والنسخة النهائية والمستهلكين، ونوسع FinalSchemaCompositionTest عند تغير عقد مشترك. اختبارات fresh وupgrade ببيانات تاريخية وهوية/codec/receipt ثابتة تحمي القبول، لا مقارنة نص الدالة وحدها. لا حذف migrations التاريخية أو تعديل بصمات لتسهيل النجاح.
6. **قفل طويل أو نتيجة على أساس قديم:** المعاملة لكتابة/تحقق قصيرين. الاتصال بالمزود أو LLM خارج الأقفال، ثم تأهيل المدخلات والحق عند إكمال النتيجة/الفعل. نحافظ على ترتيب الأقفال المعتمد؛ لا global lock أو عزل أضعف أو مهلة أطول لعلاج عرض غير مشخص.
7. **المعالجة الخلفية والتأثير الخارجي:** الطابور قد يعيد التسليم؛ middleware يمنع تداخلًا ضمن نطاقه ولا يحقق exactly-once عند مزود خارجي. عند إدخال فعل جديد نثبت هوية الأمر والسجل الدائم والحالة والمصالحة. after_commit يحدد توقيت الإرسال، ولا يغلق بمفرده فجوة crash بين commit والإرسال. نعيد استعمال سجل pending/receipt/recovery الملائم؛ outbox محلي للعملية مبرر فقط إذا بقيت فجوة تسليم مثبتة، لا event platform عام.
8. **قرار اقتصادي زائف:** مصدر ومعيار وفترة وعملة ووحدة وتأخر وإرجاع ودرجة تحقق لكل حساب ذي أثر. العرض بسعر عند التواصل ليس صفرًا؛ طلب منسوب ليس تحصيلًا؛ تقليل CPL ليس تحسن المبيعات. لا يُفرض مخزون/CRM على كل نشاط لمجرد إمكانية التكامل.

PrincipalContext يرتبط بالـbackend PID وXID ويصدر ticket عبر اتصال سلطة، وقد يبني اتصالًا مستقلاً عند وجود معاملة سلطة. هذه تبعية تشغيلية حساسة عند تغيير pooling/عمال دائمين، وليست ثغرة مثبتة. قياس الموارد يجب أن يحتسب هذه الاتصالات وفترات حياتها، لا عدد HTTP فقط.

| اتصالات القاعدة | قياس الاتصالات أولًا؛ pooling محتمل حسب الحمل | PgBouncer session/transaction mode بعد تأهيل | لا statement pooling: يمنع المعاملات متعددة العبارات. transaction mode يحتاج فحص خصائص الجلسة وPID/XID والتذاكر والاتصالين [S12] |
| عمال HTTP دائمة | إبقاء آلية التشغيل القائمة في هذه المهمة | Octane/FrankenPHP/RoadRunner عندما يثبت عنق HTTP | تكرار طلبات A/B على العامل نفسه، reset للهوية/الاتصالات/singletons، memory soak ومقارن قياسي؛ لا switch لمجرد وعد أداء [S11] |
| الرصد | سجل العملية والمدة والرفض/الانتظار/الطابور بحدود بيانات آمنة، وأدوات PostgreSQL/المتصفح القائمة | OTel/منظومة metrics عندما يلزم ربط خدمات أو SLO تشغيلي | لا logging لمحتوى أسرار/محادثات/حقل خاص؛ حد cardinality للتسميات، لا business IDs في labels عامة |
| التحديث | lockfiles وCI وترقيات مدعومة قابلة للمراجعة؛ **تقييم Node26 مستقلاً** | جمع ترقية رئيسية مع تغيير منتج | يخلط مسببات الانحدار ويمنع المقارنة؛ الإصدار الأعلى لا يثبت الأفضل لهذا العقد |

PgBouncer يدعم protocol-level prepared plans في transaction mode عند ضبط max_prepared_statements؛ لا نعمم أن كل prepared statement غير مدعوم. SQL PREPARE وبعض session features مختلفة. إرشاد pooling العام أو أرقام تحسين من مقال ليست benchmark لهذا النظام. تنطبق احتياطات RLS على role وowner وSECURITY DEFINER وsearch_path الفعليين؛ لا نزيلها لتسريع الاستعلام [S05,S12].

## 7. خطة الأداء التي تمنع التحسين العشوائي

**الأداء الحالي غير مقاس هنا.** لا نثبت بطئًا أو تسريب ذاكرة من قراءة كود، ولا نعتمد نجاح Foundation كاختبار حمل. ملف surfaces.sql يضم حدود صفحات32/64/65 في مسارات، وتجميعات catalog وفي بعض الروابط؛ هذا يحدد ما نقيسه، لا يثبت أن القوائم كلها غير محدودة أو أن JSONB عيب.

قبل قياس الحزمة يثبت: نسخة الكود/lockfiles، الجهاز، CPU/RAM/قرص وذاكرة الحاوية وshared memory، PHP/PG minor، أدوار الاتصال، config الفعلي المنقح، dataset وحجم/skew وتاريخ/صلاحيات، cold/warm، التزامن، وأدوات القياس. تستخدم قاعدة اصطناعية معزولة فقط؛ لا EXPLAIN ANALYZE أو ضغط على بيانات المالك. EXPLAIN ANALYZE ينفذ الاستعلام، وROLLBACK لا يضمن محو أثر خارجي؛ لا نستعمله على دالة ذات أثر غير مفحوص.

| التجربة اللاحقة | ما تفصله | القياسات المطلوبة | ضابط القبول |
|---|---|---|---|
| B1 فتح/تبديل Business وcatalog | payload/تحقق سلطة/عرض UI | p50/p95، حجم الرد، عدد SQL ووقت/rows/buffers، long tasks وطلبات مكررة | ميزانية تسجل قبل التغيير من baseline وهدف الرحلة؛ لا payload خاص في catalog عام |
| B2 تاريخ وعروض وأسواق | أثر الحجم والتصفية والصفحات | خطة query بالدور الفعلي، scanned/returned، indexes، ضغط JSON/DOM | pagination مستقرة وحدود payload، لا SQL داخل loop يتزايد لكل صف بلا حاجة؛ لا فهرسة كل حقل مسبقًا |
| B3 قراءة/تصحيح/سحب متزامن | انتظار حقيقي أم bootstrap بطيء أم deadlock | PID/XID/blockers، وقت القفل، نتيجة بعد السحب، عدد الاتصالات | نفس شروط العزل؛ observation حقيقي للانتظار. لا تخفيضها أو زيادة مهلة لإخفاء الخطأ |

| B6 تبديل نشاط/هوية وrefresh | أثر cache/سباق الرد/BFCache | رد متأخر، إلغاء، عرض سابق، إعادة تأهيل، memory/حجم DOM | لا عرض غير مؤهل أو تكرار أمر؛ الأداء لا يتقدم على الخصوصية |
| B7 أول مهمة AI | فائدة نوعية وكلفة مقارنة بالبديل | صحة حقول/استشهادات، امتناع، latency/usage، اختلاف اللغة، timeout/provider failure | معيار مهمة واقعي ومقارن بلا AI؛ لا fake/stub كدليل جودة السوق أو النموذج |

تختار للحزمة أحجام صغيرة وممثلة وحدود توسع مع skew وتعدد أدوار وحالات رفض، وتكتب أرقامها قبل التشغيل بحسب المشهد المعروف. لا نخترع SLO «100ms» أو قدرة إقليمية بلا baseline. للويب نستعمل LCP/INP/CLS ومعايير web.dev كمرجع:2.5s/200ms/0.1 عند p75 بحسب mobile/desktop؛ قياس مختبر واحد لا يثبت توزيعات مستخدمين حقيقيين [S15].

ذاكرة PostgreSQL ليست shared_buffers وحدها: قد تتكرر work_mem لعمليات فرز/hash ولجلسات وعمال متزامنين؛ hash_mem_multiplier مؤثر. نفحص limits والقرص/temp وshared memory وعدد الاتصالات معًا، دون افتراض أنها سبب أي إخفاق تاريخي. لا زيادة عامة للذاكرة/المهل ولا تعطيل parallel/RLS دون دليل قياس وقرار محدد [S06].

## 8. AI والأتمتة: مسار حديث قابل للاختبار

يفصل أول عقد AI المهمة/السياق المأذون عن adapter النموذج. المخرج schema يراجع خارج النموذج؛ المراجع حقيقية وذات حق حالي، وتصنيف مقترح يؤكده صاحب التصريح. الحقوق والمبالغ والحساب والمقارنة والقرار المصرح به لدى أصحابها. schema لا تمنع هلوسة أو حقن تعليمات وحدها. يختبر النص الخبيث داخل دليل، ومحاولة tool scope مزور، وبيانات نشاط آخر، وفشل النموذج، وانتهاء الحق أثناء العمل [S13,S14].

يبقى SDK واتصال المزود وبيانات اعتماده عند حد التكامل خارج مسؤوليات Core المحمية؛ لا تدخل كائنات النموذج أو provider DTO إلى مالك حقيقة النشاط لمجرد سهولة الاستدعاء. لا يلزم إطار adapters عام لكل مزود محتمل: يحدد عقد الأداة الفعلية الحد الأدنى وقابلية اختبار البديل أو تعطيل الاتصال.

لا نفترض أن fallback إلى مزود ثانٍ مباح؛ يراجع حق إرسال البيانات والاحتفاظ/التدريب/الإقليم والميزانية لكل مزود. سقف تكلفة ووقت وحجم وتكرار، وفصل بيانات المعلن عن بيانات التقييم والتدريب، شرط للقدرة المعنية. لا نُدخل تكلفة مدفوعة عبر Commercial HOLD باعتبار UNKNOWN استعمالًا غير محدود. يمكن للحسابات المحلية والمنفعة المستقلة أن تتقدم دون ذلك.

الأتمتة تبدأ بسياسة أو قرار محدد، ومورد وحالة وسقف وسلطة وانتهاء، وأمر وإيصال ومصالحة. قبل فعل مؤثر تعاد أهلية الدليل والحق وإصدار المورد؛ إذا انتهى الدليل بعد إرسال الفعل فلا ندعي أنه لم يحدث: نصالح ونقرر تعويضًا مستقلًا إن لزم. لا تضمن أي عملية تعويض استرداد الإنفاق أو محو التعرض السابق. لا إعادة محاولة كتابة عمياء تحت اسم reliability.

## 9. ترتيب العمل وبوابات الإيقاف

1. **عقد P1 المحدود:** جرد الحقول والكاتب والقارئ والنسخ والحقوق الموجودة؛ اختيار عرض/سؤال ومستهلك فعلي. تحديد أثر التعدد والمجهول والتصنيف والخصوصية. يحسم قرار محمي فقط إذا كشف العقد تغييرًا فعليًا في السلطة أو المعنى المعتمد.
2. **شاهد سلوك قبل التوسيع:** إدخال/قراءة/تصحيح عبر أوامر المنتج مع حالتي اختلاف دلالي وثبات، دون منح fixtures حق issuer غير موجود. المستهلك يختبر العقد لا يتظاهر بميزة سوق كاملة.
3. **أقل تعديل متصل:** types وHTTP وSQL/ترحيل عند لزومه وVue ضمن الملاك. لا إضافة تقنية من جدول البدائل إلا بحاجتها المثبتة. جزء ثقيل async بحدوده؛ التحقق/الحفظ القصير synchronous.
4. **قبول الحزمة المعنية:** اختبارات سلوك وعزل وسحب وتزامن وفشل، fresh/upgrade/final composition إذا تغير العقد/SQL، ثم UI/متصفح/RTL وحراس Core وAPI والبوابات المطلوبة. إعادة استخدام ما بقي مكافئًا؛ Foundation النهائي عبر CI المعتمد عند التغيير المؤثر، دون إعادة محلية تلقائية.
5. **تقدم الفروع:** بحث NEXT-01 قائم ومناسب لـP3–P5؛ لا يعيد هذه الدراسة العامة. AI يؤهل بمهمة حقيقية. غياب issuer لفرع direct-source يمنع حكمه فقط؛ لا يمنع سياق Business أو معرفة مستقلة مرخصة.

نوقف الادعاء أو القدرة المتأثرة عند غموض مالك الحقيقة/السلطة، أو عجز عن إثبات الحالة المجهولة/العزل، أو تغيير بصمة/تاريخ بلا عقد، أو عدم وجود مصدر مشروع للمخرج الموعود. قياس الأداء مطلوب حين يعتمد عليه الاختيار التقني؛ لا يوقف كل البرمجة انتظارًا لحمل إنتاج غير موجود. إذا ظهر baseline defect جديد يثبت بأصغر probe ويقارن بالمرجع الناجح قبل توسيع التحقيق.

## 10. النتيجة وحدودها

**المسار الموصى به:** عقد سياق صغير متصل بمنفعة، فوق المكدس الحالي؛ بيانات وحقوق وإصدارات واضحة؛ أوامر قصيرة ومهام ثقيلة محدودة؛ قرار وفعل منفصلان؛ أداء يقاس عند حد التأثير؛ تقنيات حديثة تختار بالمقارنة لا بالاسم. لا ترقية رئيسية أو إطار جديد شرطًا عامًا للبدء.

مُنجز في هذه الدفعة: دراسة النصوص والحدود، تحقق lockfiles وCI، قراءة مصادر رسمية مختارة، سجل24 خطرًا وخطة تمييز/قياس واختيارات مؤجلة بشروطها. غير منجز: تنفيذ P1، reproducer تشغيلي جديد لـG-01، اختبار حمل أو OOM، تجربة SDK/LLM/مزود حي، تحديث dependencies/audit حديث، أو قبول كل الأقسام. لا ادعاء «خلو100%» أو أمان شامل أو جاهزية إنتاج.

هذه نتيجة كافية للانتقال إلى **تأهيل العقد التنفيذي المحدد** دون إعادة دورة دراسة تقنية عامة. نتائج القياس أو البحث اللاحق تعيد فتح القرار الذي تؤثر فيه فقط. يحفظ `EVIDENCE.json` مرجع الملفات المقروءة وبصماتها وفحوص الوثائق؛ لا تساوي هذه الفحوص اختبارات المنتج أو benchmark.
